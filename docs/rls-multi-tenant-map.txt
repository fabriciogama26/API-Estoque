RLS / Multi-tenant map (pessoas, materiais, entradas, saidas)
=============================================================

Objetivo
--------
- Cada tenant (owner + dependentes) enxerga apenas seus dados.
- Master enxerga tudo.
- Tabelas com account_owner_id sao tenant.
- Catalogos (sem account_owner_id) sao leitura publica (SELECT) apenas.
- Nenhum DELETE via app.

Fluxo de owner (como o banco identifica o tenant)
-------------------------------------------------
- auth.uid() vem do token do frontend.
- current_account_owner_id() resolve o owner:
  1) app_users_dependentes.auth_user_id -> owner_app_user_id
  2) caso contrario: app_users.parent_user_id ou app_users.id
- my_owner_id() deve delegar para current_account_owner_id().

Politica de reposicao (2026-09)
-------------------------------
Tabelas (owner-scoped, RLS habilitada, sem force, escrita somente por RPC)
- inventory_policy: uma linha por account_owner_id; ausencia = valores padrao.
- inventory_material_override: override de minimo/maximo por material; um nao revogado por material.
- inventory_policy_history: historico gravado por trigger (antes/depois, motivo, ator).
- SELECT: master ou (account_owner_id = my_owner_id() e has_permission('estoque.read')).
- INSERT/UPDATE/DELETE: revogados de anon/authenticated; somente RPCs SECURITY DEFINER.

Helpers
- forecast_assert_owner_access(p_owner_id): 42501 se owner da sessao nulo ou diferente (libera master e service_role).
- inventory_policy_assert_manage(p_owner_id): acima + has_permission('estoque.politica.manage').

RPCs
- Leitura (tenant da sessao): rpc_reposicao_itens, rpc_previsao_compra_sugerida, rpc_previsao_gasto_mensal_auditar,
  rpc_inventory_policy_get, rpc_inventory_policy_history.
- Escrita (estoque.politica.manage): rpc_inventory_policy_update, rpc_inventory_override_set, rpc_inventory_override_revoke.
- Internas sem acesso para authenticated: _inventory_reposicao_calcular, _rpc_previsao_compra_sugerida_impl,
  _rpc_previsao_gasto_mensal_auditar_impl, inventory_policy_effective.

Controle de Validades (2026-09)
-------------------------------
Tabelas (owner-scoped, RLS habilitada, escrita somente por RPC)
- requisitos_controle, requisitos_aplicabilidade, requisitos_realizacoes, requisitos_dispensas,
  requisitos_config, requisitos_historico: SELECT = master ou (account_owner_id = my_owner_id() e has_permission('validades.read')).
- requisitos_alertas_envios: sem policy para authenticated (somente service_role).
- INSERT/UPDATE/DELETE revogados de anon/authenticated; nada concedido a anon.
- FK composta (account_owner_id, requisito_id) -> requisitos_controle(account_owner_id, id).
- Triggers bloqueiam cargo/setor/centro/pessoa de outro tenant em regras, realizacoes e dispensas.

Helpers
- validades_assert_access(p_owner_id, permissao): forecast_assert_owner_access + has_permission (libera master e service_role).
- validades_pode(permissao): usado para devolver flags de acao a tela.
- Internas sem acesso para authenticated: _validades_base, _validades_filtrada, _validades_pessoas_ativas,
  validades_hoje, _validades_realizacao_json, _requisito_json, _requisitos_config_json, _validades_regra_json.
- Alertas (somente service_role): _validades_alertas_candidatos, rpc_validades_alertas_owners,
  rpc_validades_alertas_reservar, rpc_validades_alertas_finalizar.

Permissoes
- pcsmo.controle_validades -> validades.read, pessoas.read
- pcsmo.requisitos_controle -> validades.read, validades.requisitos.manage, pessoas.read
- validades.registrar / validades.renovar / validades.requisitos.manage -> validades.read
- validades.regras.manage -> validades.read, validades.requisitos.manage

Estado atual e problemas observados
-----------------------------------
- Materiais: funcionando via RPC full + preflight.
- Pessoas: ainda pode ocorrer 42501 se:
  - RPCs de catalogo nao estiverem aplicados, ou
  - front ainda chamar SELECT direto (ver api.js),
  - ou owner resolver NULL (dependente sem vinculo em app_users_dependentes).
- Saidas/Entradas: dependem de RLS owner e permissao correta.
